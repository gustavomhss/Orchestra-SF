## Why the catalog is unavailable

The earlier R12 journey reached the original catalog endpoint and received HTTP 503 with the closed result `SF_NATIVE_PHASE_UNAVAILABLE`. That response was useful diagnostic evidence, but the former F01 health check had qualified only publication, Location and C08 infrastructure. A fresh catalog request can enter the original native phase through `issue` / `withPlanning` and activate planning. Infrastructure alone does not attest the global runner fence, engine and scope prerequisites of that path.

The bridge collapses several original failures into the same unavailable response. The report therefore does not infer a specific provider, credential, filesystem or case failure from the 503. More significantly, no adequate original observation API was found that could certify all global catalog prerequisites without entering planning, issuing a phase, resuming work, creating a session or performing an operation. The final health reader consequently omits `routines.catalog`; original context composition reports it unavailable and non-operational.

This is implemented in the [routine health reader](https://github.com/gustavomhss/Orchestra-SF/blob/fd46215487c40f2fb50cd0b4057333cbece307ec/apps/cli/src/sucafina-product/native-ui/routine-health.ts) and the [UI64 contextual helper](https://github.com/gustavomhss/Orchestra-SF/blob/fd46215487c40f2fb50cd0b4057333cbece307ec/packages/app-shell/src/orchestra/chapters/sucafina/host/routine-catalog-unavailable.tsx). The helper requires an original ready owner, a parseable supported route, compatible owner query values and explicit catalog unavailability; the owner runtime invokes it only in the original denied view. It cannot admit the leaf or run planning. R12 is retained below as the reason for this correction, not as final catalog qualification.
