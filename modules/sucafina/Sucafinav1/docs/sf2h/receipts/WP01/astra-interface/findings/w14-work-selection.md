## Own implementation

`case-work-selection.ts` is mounted on the authorized case page in `interface/http.ts`. It presents only record references already returned by the real case projection. Checkbox values use reference digests; no record reference, recipient authority or selection token is synthesized from a label. The selected dates must fit the case horizon and every selected record. The HTTP consumers use the published `collaboration-selection-list`, `-selection-version`, `-selection-create` and `-cycle-read` envelopes.

A save freezes its body, storage version and key. A lost response permits only an explicit exact retry. Listing saved selections does not convert an uncertain save into success and does not send another mutation. A first `409 conflict/selection-not-committed` is the producer's explicit C08 precommit rejection: the consumer requires **Review rejected selection**, with authorized rereads, before enabling a new intention. An already uncertain retry remains exact for that same response. Other 409/503 results are not interpreted as evidence of no commit.

The create contract accepts a case reference but no expected case version. The consumer therefore rechecks the real authorized HTML projection before creating and after receiving an acknowledgement. If the case changes in that interval, it reports that the selection was saved but the decision changed, retains the entries, and does not present the selection as the case the user reviewed. A received acknowledgement never becomes a replay merely because its following read fails.

The new work-list container and `workDestinationScript` purge the complete private list after a real 401/403, abort outstanding reads and fence late responses. The case-selection consumer also broadcasts an observed 401/403 or principal/accessRevision change to the other protected consumers, outside its revocation listener; the real logout test observes exactly one event in addition to all existing purge assertions. A transient failure preserves the list and restores only the relevant button. The deadline covers the response body. Unmounting closes the consumer as well.

The recipient fixture export error from W13 is fixed by composing `createDashboardRecordEvidenceHost` and `createDashboardRecordSourceIssuer` over the same real authority and durable source persistence. The retained BCS does not export `dashboardRecords`. Its cases/evidence remain real; no callback is substituted for authorization or state. The two recipient tests and their assertions are unchanged.
