# Review integration

## Production composition and consumers

`createReviewApplication` composes the agenda, historical C06 comment capture, durable C05 review store, C16 descriptors, human preserve/closure commands, comparison, artifact storage and HTTP handler. The existing authenticated host supplies its state, UI/human authorities, C17 evidence service and real C02/C06 producers. `app.http(request, surface)` returns a response only for the review modes. Register `app.descriptors` in the existing native/MCP registry; UI preview, report preparation and artifact admission already call the same `dispatchSfCapability`. This factory starts no listener, creates no identity and grants no capabilities.

Mount `createReviewPreparationView` at the existing Prepare review/Generate Report entry, supplying authorized `ReviewAgendaItem` selectors. It previews periods, counts, captured values and separate comments; supports section order/removal and explicit record removal; preserves only on the human action; and opens a new revision explicitly. An agenda fixes its preview content for fifteen minutes. Changed source values/versions/comment versions invalidate the selection instead of preserving numbers different from the preview. A fresh selection is required after expiry or drift.

Mount `createReviewBrowser` to present an existing review. Pass the host's update notification and explicit new-revision action, plus authorized source and review-section navigation. The comparison includes canonical current forwarding state from `createReviewClosurePort`; missing handoff producers yield explicit unavailable coverage. Call `refresh` on access changes and dispose on navigation/revocation. The host must enforce current authority when opening any source.

For persisted resident `DecisionBrief` and `MeetingMaterialProposal`, inject the real `createSfContributionReader` and, when needed, decision result store into `createReviewApplication.contributions`. `review-contribution` then reads the envelope, checks its case/digest, and reopens every referenced result/review/artifact under current authority. `createReviewContributionView` consumes that route and exposes real navigation/download actions. A DecisionBrief's result references are never treated as review IDs. No synthetic resident run or consumption receipt is generated.

The shared mount in `src/surfaces.ts`, native registry and resident-session composition remain owned by WP10/WP00. This branch provides the concrete factories and route contracts but does not claim they have been mounted in that foreign file. Missing historical producer ports remain explicit refusals. See `docs/sf2h/receipts/WP07/` for the exact integration deltas, hosted check SHAs and remaining acceptance evidence.

The Chromium functional scenario selects 1–31 January 2027 through the real Planner and retains every value returned for that period. It exercises the actual review application, HTTP routes, browser consumers, local authority and SQLite persistence with a controlled evidence catalog, thread producer and host navigation adapters. Its hosted PASS in run `43530831862` qualifies only the interactions exercised in that scope. Annual browser runs remain failed and are tracked in `INTEGRATION-DELTA.md`; this scenario does not establish annual performance, historical C06 producer integration, physical C17 continuity, the WP10 installation mount or native execution.

## Authority and preservation

`createReviewPort` requires the existing protected product state and the authenticated host request for each call. `select` resolves the ordered section references against the current principal and returns domain projections and the producer’s selected record count, without recalculating values or treating metric count as record count. It must redact restricted titles, records and counts and return a non-identifying refusal when access is unavailable. `authorizeSections` rechecks the current right to each section, including empty sections whose titles or counts may be restricted. `authorizeComments` rechecks current C06 access to every captured comment. `authorizeSensitivity` rechecks the scenario, result and coverage references in any captured sensitivity. `revalidate` checks every `SourceRef`, including comment sources. `revalidateEvidence` resolves every `BusinessEvidenceRef` against current authority; historical access must be explicitly established by the source resolver. Do not implement these authorization callbacks as unconditional allows. A selection must use the same installation, project, principal, policy and access revision as its binding.

`preserve` uses the host clock plus a target incarnation, storage revision and idempotency key supplied by the authenticated host. An exact retry reads the durable receipt before consulting mutable source projections. A successful response contains the captured projection and C06 comment versions; the current conversation remains owned by collaboration. `read` rechecks source and evidence access and returns the whole review only when all captured sources remain authorized. This conservative refusal prevents counts and titles from exposing restricted content.

`createMeetingView` reads the preserved review on navigation. With the comparison port, it consumes the server-authorized result; that port rereads both reviews and revalidates current host authority before returning. The local fallback performs its own review reads and consistency checks. Mount `element` in the product shell, call `refresh` when the host detects an access or source change, and dispose the view when leaving. The host must remove the mounted view immediately when it revokes its binding. `requestUpdate` must perform a fresh authorized selection and preserve a new identity; it must not mutate the previous review.

`createReviewCapabilities` provides C16 descriptors, using the host's `SfDomainValidation`. The host must implement `artifacts.put/read` with durable private storage. It must bind bytes to the returned artifact reference, selected section refs and the preserved review, revalidate authorization at every byte download, and never expose files by an unauthenticated path. `readArtifact` returns metadata; it is not a byte-download endpoint. Register these descriptors only when the selection, evidence resolver and artifact store are composed with real producers.

When a selected view includes a chart, the host may supply the `resolveBiPresentation` result as `ReviewSection.chart`; its series values are verified against the captured projection. For a timeline, attach the real `resolveTimeline` result as `chart.timeline`; for a waterfall, attach the real `resolveWaterfall` result plus its final value ID as `chart.waterfall`. For BI11, attach the authorized sensitivity result and explicit axis units as `chart.sensitivity`. Compatible single-unit BI01 financial trajectories and BI03/BI05/BI06/BI07 bars, BI04 separate capacity/cost panels, BI08/BI10 timelines, BI02/BI09 waterfalls and BI11 evaluated sensitivity points are rendered from captured series in both formats; category bars paginate without dropping entries. Captions state series, scale, period and values. Other or incompatible chart kinds are declared unavailable in the export. The renderer consumes only the captured projection, selected sections and preserved comments. Its document output is not yet the complete product acceptance: WP05 chart presentations and WP14 expected/observed projections require their real producer handoffs, and long output requires rendered-page inspection. CI and integration evidence are tracked separately from this interface.
