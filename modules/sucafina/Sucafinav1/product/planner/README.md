# Planner product ports

The seven Planner pages remain owned by `runtime/planner.ts`: Overview, OPEX, CAPEX, Headcount, Entities & allocations, FX rates and Versions. `plannerContribution` exports that domain and its original renderer. `projectPlanner`, `simulatePlannerCommand`, and `simulatePlannerCommands` use that same domain; previews execute against a copy and do not apply changes to the source snapshot. WP06 consumes the command adapter for import preview.

`createPlannerProduct` binds the authenticated domain host, the installation's scoped source lifecycle and a coverage resolver. `issueSource(versionId, context)` issues a current actor-scoped selector in the returned evidence reference. `compareForecast` checks that source and actor before and after projection. Monthly budget, actual and outlook totals, original currency measures, USD conversions, planned FTE, HR budget and currency rates carry source evidence; missing values and rates stay absent. `plannerMonthlyPresentation` and `plannerCapacityPresentation` provide BI01 and BI04 series without recalculating money. `comparePlannerVersions` identifies matched, added, removed and incompatible components; it does not infer causes.

For a classification registry, the source evidence identifies the physical Planner version, incarnation, revision, projection fields, period and digest. A comparison of that source with itself returns the current actor-filtered components as `<line-id>:<month>` with their monthly periods, USD amounts and source identities. Its values expose the matching original forecast, declared currency and converted outlook under `<line-id>:<month>:forecast`, `:currency-declared` and `:outlook-usd`. Component and value IDs are distinct from the top-level projection field names in the source evidence. These identities and values do not assert a decision category: an authorized classification must bind category and scope to them separately and be revalidated against the current source.

`prepareMonthlyDrafts` retains text and validation errors; `previewMonthlyDrafts` sends valid rows through the real domain on a copy and retains each conflict alongside its draft. `createPlannerMonthlyHost` authenticates the real UI request and actor, admits only existing visible rows, and checks the private human intent before its preview or transactional apply. Successful rows commit through the original commands and revisions; rejected rows retain their text and conflicts.

`plannerValueRef` identifies a monthly source measure. `createPlannerScenarioInputs` resolves it through an authorized current Planner projection. A host must supply real human confirmation evidence for confirmed assumptions; the default rejects confirmation. Scenario operations are previews and do not change the official version. Coverage for a modified scenario requires a case-specific reassessment, and the result remains conditioned while assumptions or inputs are unresolved.

`preparePlannerMutation` prepares a forecast edit on an existing OPEX or CAPEX line from an authenticated scoped source and a copied domain snapshot. Its mutation checks the same actor, source incarnation, source projection, month coverage, command revision and preview digest inside the eventual transaction. `plannerPreparedRevision` reads the exact post-write row revision. The composition host retains the private scope, operation ID and preview time, and WP11 supplies human confirmation, transactional application and receipt authority; preparation alone does not apply an edit. Synthetic HR rows require their own domain path and are not accepted by this producer.

`createStoredPlannerScenarioHost` resolves C08 results against the current authorized case and matches both request and result digests to exactly one current alternative. The WP11 case coverage resolver must be supplied through `createPlannerCoverageRouter`, with a current forecast coverage source for baseline references. `createPlannerResultPersistence` can persist scenario and comparison outputs in the case store; capability handlers return `outputRef` only after a successful authorized write. Comparison persistence requires the current scenario resolver so that it revalidates both alternatives before writing; a missing resolver returns unavailable. Scenario and comparison capability handlers also return unavailable when result persistence is not configured.

`comparePlannerPreview` compares an authorized current alternative with a transient Planner preview using only the baseline's real coverage reference. Its preview metric is conditioned and carries source evidence. `createPlannerSensitivityUnits` issues independent parameter and result units from the exact operation and actor-filtered source, then binds them to the single human-registered WP11 criterion rule. `createPlannerCriterionMetric` resolves that rule to the current domain metric; unknown criteria remain independent of financial completeness. Sensitivity sampling remains a separate WP13 producer injected through `PlannerPort.evaluateSensitivity`; the Planner factory reports it unavailable until that producer is connected. These exports do not by themselves prove a native, UI, import or BI entrypoint is connected; the composition and hosted checks must establish those consumers.

`createPlannerExactThreshold` supports a single direct USD replacement of an open non-HR month with finite components and a fixed baseline. The shared save, USD conversion, outlook and ordered subtotal operations are monotone, including floating-point plateaus; the solver verifies the neighboring representable value at the frontier. The result describes a conditioned metric, not complete cost coverage. Changes to those engine semantics require a new engine version and a fresh review of the proof.
