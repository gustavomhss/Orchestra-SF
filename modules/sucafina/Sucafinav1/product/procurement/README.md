# Procurement product ports

`createProcurementPort` reads the existing Procurement domain under the current actor. `list` returns the authorized request `queue`, open `stock`, and pending `aging` projections from the same selection; an unknown stage or an unproven entry time remains unavailable. `createProcurementCollectionRegistry` issues host-held collection and stage selectors. A selector selects records and never supplies authority.

`createProcurementSourceResolver` issues individual scoped selectors backed by the persisted source registry. Its `resolveForPreparation` is host-private. It reauthenticates the Request and returns the current evidence and scope for the selected principal, policy, access revision, period, and currency. A caller must restore the same period after a restart. Legacy global-version selectors are not accepted.

Use `createProcurementCollectionMemberIssuer` to convert a current collection member into individual evidence before persisting a work item. The host must still revalidate that individual evidence at admission and on later reads. `issueForActor` reissues an individual source for a different actor only after that actor's own authorization and a physical-incarnation check; unsupported subsets and collection references remain unavailable.

`createProcurementContractSource` reads explicitly selected Dashboard Vendor Contracts through the Dashboard source owner. The source reference is issued under that owner's current authorization. A contract's vendor text does not establish a supplier relationship. Amount currency is included only when the currency field was also selected and requested.

`createProcurementSourcingEvidence` is a host-private verifier input. It reads the authorized request, offers, submitted snapshot rates, and configured scoring criteria from the current domain and uses the existing comparison producer for eligibility and ranking. Offer revisions are revisions of the parent request scope; an offer has no independent revision. Missing FX and unrecorded policy are not replaced with zero or invented requirements.

`createProcurementDecisionPreparation` assembles read-only C02 material for a dossier. It checks that the request and comparison still refer to the same source; it does not approve or apply a command. `createProcurementScenarioPreparation` prepares only an explicit PR amount replacement present in a host-authorized recorded choice with matching evidence, currency, and period. Other operation shapes are rejected rather than being mapped by name.

`prepareProcurementMutation` currently accepts `Requests/save` for the existing requisition's title, justification, and estimated amount. It runs the actual domain on a copy, checks the actor and persisted scope, and rejects unrelated changes. WP11 owns the human confirmation, the C08 atomic transaction, and the receipt. For restart-safe reconstruction inside that transaction, recover the scope with `procurementPreparedScope` and use the retained evidence, command, operation ID, idempotency key, and target observation time. `staleProcurementPreparedMutation` produces only a conflict when the currently authorized snapshot proves a changed scoped version or command revision; missing or revoked authority is not converted to conflict. `procurementPreparedRevision` returns the actual command CAS revision, not the source evidence revision. Domain audit records use the actual apply time.

`createProcurementPreparedReview` accepts a command loaded privately from an authorized decision case and returns only C02 before/after fields and evidence for the current reviewer. It reissues that source for the reviewer, proves the original scoped source remains current and maps to the same physical incarnation, and returns an `originalTargetDigest` for WP11 to check. It never exposes the executable command.

`createProcurementC12Bridge` bundles the host-private scenario preparation, review, mutation reconstruction, and receipt revision callbacks for WP11. The host must still load the recorded choice, enforce its human confirmation and current grant, and commit the domain and receipt atomically.

These ports do not themselves mount UI routes, issue human confirmation, or provide a finished C07 dossier. Their host consumers and the repository's scoped CI gate must be verified on the integrated candidate.

`createProcurementConfirmationObserver` provides the host-private `procurement-c06-v1` material selector for `status`, `subject`, `reason`, `holder`, `approvalStage`, `nextStep`, `stageEnteredAt`, and the recorded amount, currency, FX, and monetary-state fields. Issue the material source first and use its sorted evidence fields and scoped incarnation to form a confirmation scope. Status and the selected financial inputs are internal dependencies; external dependencies, `ageDays`, and other fields are unavailable. `observe` reauthorizes the current principal and checks physical continuity and equivalent material before returning the current principal's scoped evidence. `fence` is read-only and requires the enclosing all-surface transaction. The host must route `sf-procurement-c06:` references to `resolve` and install the WP10 `procurement-confirmation-v1` scoped projection; neither is supplied by the ordinary full-record resolver.

## WP04 domain composition

`projectProcurementScope` in `source-projection.ts` is the canonical Procurement scope projector. Install this function in the existing `createSfSourcePersistence({ projectScope })` composition: it observes the real domain projection at issuance, resolution, and **every committed mutation**. This is required for intermediate changes and delete/recreate protection; a read-time-only wrapper is insufficient. The same function supplies full requests (including `approvalStage`), suppliers, authorized collections, and `procurement-confirmation-v1` material. It delegates monetary values and dependencies to the domain's existing producers and never stores an alternate request model. `sources.ts`, prepared changes, and the confirmation observer consume this exact projector.

The scoped WP04 tests install this production export through the existing lifecycle seam and use the actual local store. They do not demonstrate that the common application or a native Session has installed the export. WP10 owns that mounting point. Its compatible delegation is an import of `projectProcurementScope` followed by `export const projectSfProcurementScope = projectProcurementScope` in `product/integration/procurement-projections.ts`.

`createProcurementCapabilities` preserves the closed WP00 input/output validators. The shared dispatcher remains `dispatchSfCapability`, including one-use admission, current authority, result validation, and the handler receipt. New comparison components, monetary provenance, weights, and selection require the WP00 contract producer to be integrated; unknown fields are never stripped or accepted by bypassing admission.

### Integration boundary at this handoff

The initial `astra-wp04` seed lacks the newer WP10 source routing and WP00 comparison schema. Current producer pins inspected are WP00 `72342f0efbbe099231aa2e30a964769b14e4fbb2` and WP10 `dc6bf9e4e8f3d2fa01d01c76d5575892a8ced82f`. WP10 must mount the material confirmation observer, source resolver, C12 bridge and deterministic dossier preparation in its common business-services composition. Its native Procurement analysis verifier must consume configured scoring criteria rather than reject every nonempty criteria list. These are explicit integration obligations, with no claim of native or resident acceptance from domain tests.

The controlled 30-second comprehension target and actual keyboard focus after a browser conflict require observed UI runs. A deterministic projection or HTML assertion does not establish either measurement. A conflict remains a 409 carrying the latest version and the local draft must be reviewed explicitly before reapplication; a producer's read-only dossier never approves a purchase.
