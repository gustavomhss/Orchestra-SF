# Procurement product ports

`createProcurementPort` reads the existing Procurement domain under the current actor. `list` returns the authorized request `queue`, open `stock`, and pending `aging` projections from the same selection; an unknown stage or an unproven entry time remains unavailable. `createProcurementCollectionRegistry` issues host-held collection and stage selectors. A selector selects records and never supplies authority.

`createProcurementQueuePageView` supplies the Requests and My approvals pages with that actual C02 output through the application's private `productView` hook. It prepares the read before the page transaction, then revalidates the UI grant, actor, roles, source incarnations, versions and material digests inside the authenticated page transaction. A changed or unavailable projection cannot fall back to an apparently current queue. `queue-view.ts` presents the C02 fields without deriving a second business state machine. The local host composition mounts the hook; page-scoped selectors are released after rendering, and the request hyperlink performs a new authorized drilldown.

The configured product runtime returns an explicit unavailable response while its queue service is absent, including startup/disposal. The existing standalone domain mode without a product runtime retains its renderer for compatibility; that mode is not evidence of C02 composition.

`createProcurementSourceResolver` issues individual scoped selectors backed by the persisted source registry. Its `resolveForPreparation` is host-private. It reauthenticates the Request and returns the current evidence and scope for the selected principal, policy, access revision, period, and currency. A caller must restore the same period after a restart. Legacy global-version selectors are not accepted.

Use `createProcurementCollectionMemberIssuer` to convert a current collection member into individual evidence before persisting a work item. The host must still revalidate that individual evidence at admission and on later reads. `issueForActor` reissues an individual source for a different actor only after that actor's own authorization and a physical-incarnation check; unsupported subsets and collection references remain unavailable.

`createProcurementContractSource` reads explicitly selected Dashboard Vendor Contracts through the Dashboard source owner. The source reference is issued under that owner's current authorization. A contract's vendor text does not establish a supplier relationship. Amount currency is included only when the currency field was also selected and requested.

`createProcurementSourcingEvidence` is a host-private verifier input. It reads the authorized request, offers, submitted snapshot rates, and configured scoring criteria from the current domain and uses the existing comparison producer for eligibility and ranking. Offer revisions are revisions of the parent request scope; an offer has no independent revision. Missing FX and unrecorded policy are not replaced with zero or invented requirements.

`createProcurementDecisionPreparation` assembles read-only C02 material for a dossier. It checks that the request and comparison still refer to the same source; it does not approve or apply a command. `createProcurementScenarioPreparation` prepares only an explicit PR amount replacement present in a host-authorized recorded choice with matching evidence, currency, and period. Other operation shapes are rejected rather than being mapped by name.

`prepareProcurementMutation` currently accepts `Requests/save` for the existing requisition's title, justification, and estimated amount. It runs the actual domain on a copy, checks the actor and persisted scope, and rejects unrelated changes. WP11 owns the human confirmation, the C08 atomic transaction, and the receipt. For restart-safe reconstruction inside that transaction, recover the scope with `procurementPreparedScope` and use the retained evidence, command, operation ID, idempotency key, and target observation time. `staleProcurementPreparedMutation` produces only a conflict when the currently authorized snapshot proves a changed scoped version or command revision; missing or revoked authority is not converted to conflict. `procurementPreparedRevision` returns the actual command CAS revision, not the source evidence revision. Domain audit records use the actual apply time.

`createProcurementPreparedReview` accepts a command loaded privately from an authorized decision case and returns only C02 before/after fields and evidence for the current reviewer. It reissues that source for the reviewer, proves the original scoped source remains current and maps to the same physical incarnation, and returns an `originalTargetDigest` for WP11 to check. It never exposes the executable command.

`createProcurementC12Bridge` bundles the host-private scenario preparation, review, mutation reconstruction, and receipt revision callbacks for WP11. The host must still load the recorded choice, enforce its human confirmation and current grant, and commit the domain and receipt atomically.

`createProcurementDecisionHost` composes the bridge with WP11's actual prepare/review/apply paths and the C08 receipt store. The host mounts `decision-http.ts` for explicit human preparation, review and application. The review returns material fields, not an executable command. A successful domain commit and its receipt share the transaction; reconciliation checks the case again, and a lost response can recover the same receipt without repeating the business effect. Supported prepared mutations remain the PR save fields above.

`createProcurementConfirmationObserver` provides the host-private `procurement-c06-v1` material selector for `status`, `subject`, `reason`, `holder`, `approvalStage`, `nextStep`, `stageEnteredAt`, and the recorded amount, currency, FX, and monetary-state fields. Issue the material source first and use its sorted evidence fields and scoped incarnation to form a confirmation scope. Status and the selected financial inputs are internal dependencies; external dependencies, `ageDays`, and other fields are unavailable. `observe` reauthorizes the current principal and checks physical continuity and equivalent material before returning the current principal's scoped evidence. `fence` is read-only and requires the enclosing all-surface transaction. The host must route `sf-procurement-c06:` references to `resolve` and install the WP10 `procurement-confirmation-v1` scoped projection; neither is supplied by the ordinary full-record resolver.

## WP04 domain composition

`projectProcurementScope` in `source-projection.ts` is the canonical Procurement scope projector. Install this function in the existing `createSfSourcePersistence({ projectScope })` composition: it observes the real domain projection at issuance, resolution, and **every committed mutation**. This is required for intermediate changes and delete/recreate protection; a read-time-only wrapper is insufficient. The same function supplies full requests (including `approvalStage`), suppliers, authorized collections, and `procurement-confirmation-v1` material. It delegates monetary values and dependencies to the domain's existing producers and never stores an alternate request model. `sources.ts`, prepared changes, and the confirmation observer consume this exact projector.

The shared `product/integration/procurement-projections.ts` delegates to this export. The CLI business-services composition mounts the material confirmation observer, the WP08 confirmation consumer, the WP14 evidence route, C12 and WP09's read-only sourcing dossier. Its host integration tests use the actual SQLite store and source lifecycle. This composition is a shared seam for S0 review; a passing host test does not establish native model execution.

`createProcurementCapabilities` preserves the closed WP00 input/output validators. The shared dispatcher remains `dispatchSfCapability`, including one-use admission, current authority, result validation, and the handler receipt. Comparison components, monetary provenance, weights and selection are declared in the contract producer and its officially generated output schemas. Unknown fields are never stripped or accepted by bypassing admission.

### Evidence, money and supplier privacy

Preparation archives the authorized original C02 projection under a root-private writer. Historical reads retain that original and report concrete current differences only after current authorization and physical continuity are proved. A same-name replacement does not recover old evidence or receipts. The proof of continuity rechecks the archived bytes, current scope, actor, version and canonical material digest; its short-lived observation is not a cached permission decision.

`procurementMonetaryFacts` retains the original currency of a submitted PR from its recorded approval currency. A later Settings base change does not relabel that amount or invent a new comparable amount. Missing submission currency and FX stay absent. The C06 material rule is `procurement-money-v3`. Submitted sourcing/PO values keep their recorded FX; approved and internally issued remain distinct states.

The Procurement register and purchase-order download use these same PO monetary facts. Missing or malformed amounts, ambiguous selected quotations, missing currency and unavailable FX are displayed as `Unavailable`; an explicitly recorded zero remains zero. The register retains its existing columns and adds the PO base currency, FX rate/source, monetary state and submitted approval amount/currency/rate. A later base-currency change leaves the submitted approval identified in its recorded currency while the incompatible current-base amount remains unavailable. Missing PO lines do not erase a known submitted approval or permit the export to borrow a quotation or PR estimate as the order total.

Supplier screens, projections, audit and CSV export apply the existing banking privilege boundary. All six bank fields, including bank name, account holder and bank country, are restricted together. An allowed bank change invalidates active validation and requires explicit revalidation. Activation messages name the missing business fields in readable language.

Supplier enum controls retain an already recorded value outside the current option catalog as an explicitly labeled recorded option. Saving another field does not silently replace that value with an empty/default selection; domain validation remains authoritative.

### Guided UI and sourcing analysis

The common application returns the current command revision with a real CAS conflict. Its shell preserves draft values and comments, shows field errors next to controls, restores focus and requires an explicit version review before a retry. An older save response cannot discard later edits. Conditional purchase fields remain in the form when hidden, and recorded supplier/currency/quantity are reused while negotiated order values are retained.

The Workbench sourcing form selects only request evidence attached to the authorized case and models from the host's existing catalog. Its input route prepares the actual configured scoring material and revalidates the case and source. Streaming request bodies stop at the transport limit before parsing. The verifier compares the contribution with the canonical deterministic result and current evidence; crafted output envelopes test this predicate only.

While an analysis is preparing, active or uncertain, the sourcing controller keeps the form protected from the shell's background refresh. Only a current authorized terminal read releases that guard. Generation and read sequence checks discard responses from an older start, cancellation or read. Refreshing history alone does not authorize repeating an unconfirmed start.

Execution evidence, exact product/snapshot SHAs and all 111 criterion statuses are recorded under `docs/sf2h/receipts/WP04/resume-20261113/`. Browser automation, an HTTP host test and a verifier predicate are separate proofs. Actual resident Session/SkillLoadReceipt and UI/native/MCP parity require the configured Orchestra runtime; the 30-second comprehension criteria require an actual person. A read-only dossier never approves a purchase.
